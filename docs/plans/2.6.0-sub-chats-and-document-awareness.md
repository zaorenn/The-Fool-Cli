# 2.6.0 — Sub-chats, and documents the models can actually read

Written 16 August 2026, after 2.5.10. Three requests, in the order they should
be built. Every "does not exist" below was checked against the tree on
`652f88fb4`, not remembered.

## Why these three are one release

They are the same complaint from three sides. A voice session is a place work
happens, and the work it produces has nowhere to live: the chats it starts are
loose in the sidebar, and the documents it opens are pictures rather than
things the model can read. The user's own phrasing was **"tam farkındalıklı
olmalı"** — fully aware of what it is doing. What follows is the difference
between an assistant that reports and one that knows.

---

## Part 1 — Sub-chats

**The ask.** Voice mode should look like an ordinary chat, and chats a voice
session starts should nest under it.

### What exists, and what does not

| Thing                                                               | State                                                                          |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `conversations` table (`fool-db/migrations/001_initial_schema.sql`) | 15 columns, **no parent**                                                      |
| `Conversation` in `fool-api-types/src/conversation.rs`              | `id, name, status, source, pinned, created_at, modified_at, extra` — no parent |
| Voice → conversation link                                           | `voice.boundConversationId`, a **single** id in the local config               |
| `useVoiceSessionRouter`                                             | navigates to `/conversation/<id>` and calls `bindConversation`                 |
| Sidebar                                                             | a flat list; no tree, no indentation, no grouping                              |

So the binding is one-to-one and lives outside the database. There is no
parent/child concept to extend — this is new structure, not a refactor.

### The decision that has to come first

`extra` is a JSON blob and a `parentId` could be dropped into it in an hour
with no migration. **Do not.** Two things make it the wrong choice: the sidebar
has to sort and group by it on every render, and `json_extract` on `extra` is
already how `idx_conversations_cron_job_id` works — a pattern worth stopping
rather than extending. A real column gets a real index and a real foreign key.

### Steps

1. **Migration `037_conversation_parent.sql`** (next free number; 036 is
   `project_kanban`).

   ```sql
   ALTER TABLE conversations ADD COLUMN parent_id TEXT
       REFERENCES conversations(id) ON DELETE SET NULL;
   CREATE INDEX IF NOT EXISTS idx_conversations_parent
       ON conversations(parent_id, updated_at DESC);
   ```

   `ON DELETE SET NULL`, not `CASCADE`: deleting a voice session must not take
   the transcripts of the chats it happened to start. One level only — a child
   may not itself be a parent, enforced in the repository rather than in SQL.

2. **`fool-api-types`**: `parent_id: Option<String>` on `Conversation`, on the
   create payload, and on the update payload. Rust change, so budget the
   eleven-minute cargo loop and a foolcore restage — the staged binary silently
   drifts, so rebuild through the script rather than by hand.

3. **Repository + routes** (`fool-db`, `fool-app`): accept and return it; add
   `GET /api/conversations?parent=<id>`. Refuse a parent that already has one.

4. **Voice starts children.** `useVoiceSessionRouter` currently binds one id.
   The voice session's own conversation becomes the parent, and every chat it
   starts is created with `parent_id` set. `voice.boundConversationId` stays as
   "the one being spoken into" and is no longer the only link.

5. **Sidebar.** Children render indented under their parent, collapsed by
   default, with a count. A child must still be reachable when its parent is
   collapsed — search results and deep links open it and expand the parent.

6. **Voice mode as a chat view.** The voice page becomes a conversation view
   with the HUD over it, rather than a separate page. Do this **last**: it is
   the visible half, and it is worth nothing until the structure under it holds.
   The preview panel already hosts on `/voice` as of 2.5.10, so the document
   half of this is done.

### What will go wrong

- **Orphans.** A parent deleted mid-session leaves children pointing at
  nothing. `SET NULL` makes them top-level, which is the right answer, but the
  sidebar has to not flicker while it happens.
- **The migration runs against real databases.** Test it against a copy of a
  populated one, not a fresh install — that is the failure mode that will not
  show up locally.

## Part 2 — Documents the models can read

**The ask.** Every model in the app — not just the voice assistant — must be
able to read an opened PDF or Office file and have full knowledge of its
contents. The same for the builtin browser. And when a PDF is a form, the model
must actually fill it, matching the font and size of the surrounding text.

### What exists, and what does not

| Thing                                      | State                                                                                |
| ------------------------------------------ | ------------------------------------------------------------------------------------ |
| `fool-pdf` builtin MCP                     | registered and **enabled** — read, merge, split, rotate, trim                        |
| `fool-browser` builtin MCP                 | **enabled since 2.5.10**, drives the offscreen page                                  |
| `pdfForm.ts`, `process/pdf/pdfDocument.ts` | ~290 lines, `readPdfFields` / `fillPdfForm`, **no IPC provider, no tool, no caller** |
| `documentViewer.ts`                        | opens a viewer; hands the model **nothing**                                          |
| `REALTIME_TOOLS`                           | deliberately short — "every entry is a pause in the conversation"                    |

The viewer shows the user a document the model cannot see. That is the whole
gap: `openDocument` returns `{path, name, viewer}` and the model gets a
filename. Asked what is in the PDF, it has to guess, and it will.

### Steps

1. **Text out of the open document.** One tool, `app_read_document`, over the
   already-enabled `fool-pdf` server for PDFs and `officecli` for Office. Takes
   a path and a page range; returns text plus a page count. Bounded: a 300-page
   PDF must not become one prompt. Page range, and a summary path for "what is
   this about".

2. **The open document is context.** When a viewer is open, its path and page
   count go into the turn — so "kaç sayfa?" and "özetle" work without the model
   choosing a tool first. Eval task 36 already scores exactly this and has only
   ever been fed a canned result.

3. **Wire `pdfForm.ts`.** It has been written and tested and called by nothing
   for weeks. The reason it was never wired is real and still applies: filling
   a form is a multi-turn flow, not one call. So:
   - `readPdfFields` becomes part of `app_read_document` — a form comes back
     with its fields named.
   - `fillPdfForm` becomes `app_fill_document`, taking `{path, values}` and
     answering with `filled` **and `unfilled`**. Never write over the original.
   - **Font and size.** `pdf-lib` defaults to Helvetica at a size of its own
     choosing, which is what "doldurdum" currently looks like on paper. Read the
     widget's `/DA` string for the font and size the field already declares, and
     use it. Where `/DA` says size 0 — auto-size — compute from the widget
     rectangle. This is the part the user will notice, so it is not optional.

4. **The browser reads too.** `browser_read` exists. What is missing is that a
   PDF or a document opened in the offscreen page falls back to the same
   extraction as step 1 rather than returning the page chrome.

### What will go wrong

- **`REALTIME_TOOLS` is a budget, not a list.** Two new entries is two more
  pauses in a spoken conversation. Measure before and after.
- **A filled form that looks filled and is not.** Task 21 already scores this:
  the tool succeeds, two fields are empty, and the model reports it complete.
  The `unfilled` list is what stands between the user and an unsigned form
  handed in.

## Part 3 — Seeing and clicking, and asking before it remembers

**The ask.** The assistant should see and click links on YouTube and web pages,
and: _"favori şarkım bunny girl akasaki"_ → search, find the best-known video,
play it, show it and ask **"bu mu?"**, and save it only if confirmed.

### What exists

The browser is on by default now, and it has the eighteen commands this needs —
navigate, read, click, scroll. Eval task 26, `Bunny Girl'ü çal`, already exists
and scores "it plays; a search page is the thing this tool exists to stop".
`app_remember` and `app_rule` already separate a fact from a standing
instruction.

So this part is mostly sequencing, not new capability.

### Steps

1. **A link is a thing, not text.** `browser_read` returns prose. It should
   return the links with it — text, href, position — so "üçüncüsüne tıkla" and
   "en çok izleneni aç" are answerable without a screenshot.
2. **Play, then ask.** The flow is search → pick → play → _show and ask_ →
   save on yes. The confirmation is the point: the user asked for it explicitly,
   and it is the difference between an assistant that acts and one that decides.
3. **Save only on yes.** `app_remember`, and only after the user says it is the
   right one. A preference recorded from a guess is worse than none — it comes
   back later as something they said and did not.

### What will go wrong

- **Autoplay.** The offscreen page has no user gesture; a video may refuse to
  start. Check this **first** — it decides whether "play it" means playing it
  there or handing it to the visible browser panel, and that changes the design.
- **"En bilindik".** There is no popularity field in a scrape. View count where
  it is shown, first result otherwise, and the confirmation step is what makes
  a wrong pick cheap.

## Part 4 — Everything the ACP agents can do

**The ask.** The Fool's own assistant should have every capability the Hermes
agent has — watching a YouTube video and summarising it was the example given.

> **The enumeration in step 1 has been done.** See
> [`hermes-capability-parity.md`](hermes-capability-parity.md): 57 toolsets, 81
> tools, and The Fool sees 29 of them over ACP. `video_analyze` and the seven
> `spotify_*` tools already exist in Hermes and ship in no distribution at all.
> Read that document before this section — what follows is the reasoning that
> led to it.

### The honest starting point

Hermes is not this repo's code. It is a builtin **ACP agent** — row `55f3ed1c`
in `001_initial_schema.sql`, `binary_name: hermes`, driven over ACP like Codex,
Snow, OpenClaw and the rest. Its capability list lives in that binary, not here,
and **this plan will not guess at it.**

So step one is not building anything:

1. **Enumerate, do not assume.** ACP advertises the agent's tools at session
   start. Connect to Hermes, capture the advertised list, and write it into this
   document. Do the same for the other builtin ACP agents. Until that list
   exists on paper, "everything Hermes can do" is not a scope, and anything
   built against a remembered feature list will be built against the wrong one.

2. **Then sort each entry into one of three.**
   - _Already ours_ — the voice assistant has an equivalent. Nothing to do.
   - _Worth having ourselves_ — build it, and it belongs in `REALTIME_TOOLS`
     only if it is worth a pause in a spoken conversation.
   - _Worth delegating_ — route it to the ACP agent instead of reimplementing
     it. `app_ask_jester` is already this shape. A capability that runs for
     minutes is nearly always this row, not the one above.

   The third option is the one that gets forgotten, and it is usually right.
   Parity does not mean reimplementation.

### Watching a video, since it was the example

Nothing here handles video today. `grep` for `youtube` across
`packages/desktop/src` returns nothing; the `transcript` hits are all speech
transcripts from the voice pipeline. This is new, and it is a good first entry
because it exercises the whole stack Part 2 and Part 3 build.

The route, cheapest first:

1. **Captions when they exist.** Most videos have them, they are text, and they
   cost one fetch. The offscreen browser can already reach the page.
2. **The local ear when they do not.** Whisper Turbo is already installed on
   this machine and already used by the voice pipeline. Audio → transcript →
   summary, entirely local, no key.
3. **Summarise from the transcript, and say where it came from.** "Captions" and
   "I listened to it" are different claims with different reliability, and the
   assistant must not blur them. A summary of a video it could neither caption
   nor hear is a refusal, not a guess.

Long videos are the trap: an hour of speech is far past one prompt. Chunk,
summarise per chunk, then summarise the summaries — and report the duration, so
"özetle" on a three-hour stream is a decision the user makes rather than a wait
they discover.

### What will go wrong

- **Reimplementing Hermes.** The temptation is to build every advertised tool.
  Most of them should be delegated; some of them the app already has under a
  different name. The sorting step in 2 is the actual work.
- **A capability list from memory.** Including this one. If step 1 has not been
  run, nothing in this section is a specification.

## Order

Part 2 first. It is the one the user hit today, it needs no schema change, and
`pdfForm.ts` is already written. Part 3 second — it is mostly sequencing over a
browser that is already on. **Part 4's enumeration step runs alongside both**,
because it is a half-hour of connecting to an agent and writing down what it
says, and everything else in Part 4 is unscoped until it is done. Part 1 last:
it is the largest, it is the only one touching Rust and a migration, and nothing
else waits on it.

## Already shipped in 2.6.0

Three items landed before the rest of this plan, because they were faults
rather than features:

- Clicking a PDF/Word/Excel/PPT in the workspace explorer opens it. It passed
  neither content nor `file_path`, so it opened blank every time.
- `openDocument` checks the file exists, so a document the model never wrote is
  no longer reported as open.
- `playOnSpotify` wakes Spotify and retries instead of returning `no-device`
  and letting the model guess.

The third is the template for the rest of this document. **The model was not
underprompted; the tool was underbuilt.** A tool that returns a bare failure for
a recoverable state hands a 9B model a puzzle it will solve by improvising with
the screen, and no amount of persona text fixes that. Before adding a sentence
to `personas.ts`, check whether the tool could simply have done the right thing:
resolve the target, wake the device, read the file, name the fields.

## The rule this release is written under

Every fix in 2.5.9 passed the suite while broken, because each test was a mock
written from the same assumption as the code. Three of them. For everything
above: **launch the app and watch it happen.** A test that mocks the channel the
code publishes on cannot falsify the code. Where a mock is unavoidable, mock the
operating system or the network — never the app's own seam.
